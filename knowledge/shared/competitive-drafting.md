# 竞争性起草与候选比较

读取时机：主 Agent 判断一个设计或产品类缺口是否值得多候选起草，以及准备候选任务包、组织候选比较或综合候选时读取。

## 为什么用多候选而不是打分

同一模型给单一方案打质量分不可靠：生成者与评估者盲区重合，分数会向"看起来像好方案"的文风漂移。相对判断比绝对打分稳定得多——"A 和 B 哪个更好、为什么"有真实判别力，"这个方案值多少分"没有。因此本流程的形态是：强制不同起点的并行候选 → 两两相对比较 → 综合，全程不出现绝对分数。

## 触发条件

同时满足以下三条时，主 Agent 可以用竞争性起草替代该缺口的单一 `draft`：

1. Medium 或 Heavy 的设计或产品类专业缺口；
2. 结构（对象归属、IA、主流程、数据边界或方案取向）存在两个以上合理答案，或方案质量会实质改变用户可见结果；
3. 不是对既有已确认模式的严格复用。

用户明确要求"多出几个方案比较"时直接触发。以下情形不触发：Light；唯一合理解的机械补齐；已进入 `design-proposal-loop` 的 Proposal（该循环自带 Panel 与独立裁决，不叠加本流程）；上游语义尚未 ready（先按 lifecycle 补缺口，多候选不能替代缺失的事实）。Light 的实现做法选择按 [`.codex/rules/lifecycle.md`](../../.codex/rules/lifecycle.md) 的“起点分叉”处理——主 Agent 自己列 2–3 个做法并给推荐，不派候选实例、不做 `compare`，两者不叠加。

## 候选生成

- 同一角色派 **2 个**（最多 3 个）全新实例，`draft` 模式；除强制先验一栏外任务包完全相同，都附质量线与适用判例。
- 候选实例互相不可见：不共享彼此的草稿、思路或存在。
- 每个实例分配一个不同的**强制先验**作为探索起点，从下列正交先验中挑选真的会改变本题答案的两三个：
  - 首次理解优先——低上下文用户第一次就能走通；
  - 高频效率优先——熟练用户的步数与打断最少；
  - 失败与恢复优先——中断、出错、误操作后的代价最小；
  - 最小结构优先——最少的新对象、新页面、新概念；
  - 数据与一致性优先——状态、并发与持久化语义最不容易出错。
- 先验只约束探索起点，不改变其它一切：候选仍须满足质量线全部判据、遵守已确认事实，不得为贯彻先验而牺牲两者。
- 温度式的重复采样不算候选——两个实例拿同样的任务包跑两遍探不开解空间，先验差异是本流程的成立前提。

## 候选比较

- 派一个**未参与起草**的全新实例执行 `compare` 任务（模式定义见 `role-conduct.md`）：默认同角色；缺口本质是跨专业权衡时可选相邻角色（如体验候选由技术架构师比可实施性）。
- 比较者输入只有：全部候选、质量线、任务包中的已确认事实。不给出主 Agent 或任何人的倾向。
- 返回：按质量线逐维的相对判断（哪个更好 + 证据 + 用户可见影响）、总体推荐、败者中值得嫁接进胜者的具体项、所有候选共同缺失的内容。**不打绝对分**，不重写方案。
- 比较结论与候选一样是 `agent_proposal`，不因"比较过了"获得更高地位。

## 综合与确认

- 主 Agent 以推荐胜者为骨架，嫁接败者的可取项，综合成唯一方案；综合稿仍是 `agent_proposal`。
- 候选之间的真实结构差异不因综合而消失：它们正是 lifecycle 要求向用户展示的"多个合理答案的实际差异"，作为待确认差异随综合稿一并交用户，由用户定夺后才可签署。
- 共同缺失项按缺口性质处理：属于本角色的发回 `revise`；属于其它专业面或需要用户决定的交回相应流程。

## 成本与降级

- 候选上限 3 个；默认 2 个已足够，第 3 个只在前两个先验都明显偏科时追加。
- 并发不足时按串行的隔离新实例执行，并在记录中如实标注串行。
- 两个候选实质趋同（结构决定一致，仅措辞与细节差异）时：记录趋同结论，视为解空间比预判的窄，不追加候选，直接按单一方案走后续确认。
- 比较者分不出高下且没有共同缺口时，不逼出一个胜者：把两案差异作为待确认差异直接交用户。

## 完成标准

- [ ] 触发有据：三条触发条件或用户明确要求，记录在任务判断中。
- [ ] 每个候选的先验不同、实例全新、互相不可见。
- [ ] 比较者未参与起草，输出为相对判断与可嫁接项，无绝对分数。
- [ ] 综合稿保留候选间真实差异并交用户确认后才签署。
- [ ] 候选数不超过 3；趋同、平局与串行降级如实记录。
