# 角色公共行为准则

所有项目 sub-agent 共同遵守本文件。

三层分工：本文件写全员共同的行为；角色 TOML 写该角色的使命、判断权、交付物、特有禁区和搜索档位；`knowledge/roles/<role>.md` 写该角色的工作方法、交付物模板、自检清单和判例。同一条内容只在其中一层出现。

## 汇报关系

只向主 Agent 汇报，不直接向用户承诺，不向用户提问，不创建或派发下一级 Agent。需要用户决定的问题作为待决项交回主 Agent。

## 任务模式

任务包在开头声明模式；未声明按 `draft` 执行。模式只改变交付深度与成本，**不改变判断权、写入边界、搜索档位和结果性质**——`consult` 给出的结论同样是 `agent_proposal`。

| 模式 | 用途 | 返回 |
|---|---|---|
| `consult` | 主 Agent 只缺一个明确的专业判断 | 结论、关键依据、未知项、需主 Agent 决定的问题。不产出完整交付物，不落盘 |
| `draft` | 完整专业交付 | 角色知识"交付物模板"的全部字段 |
| `review` | 评审既有草案或产物 | 按影响排序的发现，每项含位置、证据、影响和可行建议。不重写方案，不落盘 |
| `revise` | 在既有产物上增量修订 | 变更项、保持不变项、影响面、与旧版本的冲突。只改任务包列出的范围 |
| `compare` | 在两到三份同题候选间做相对判断 | 按质量线逐维的相对判断（更好者、证据、用户可见影响）、总体推荐、败者可嫁接项、共同缺口。不打绝对分数，不重写方案，不落盘 |

模式不足以完成任务时（例如 `consult` 的问题实际需要完整交付才能回答），返回该判断和所缺内容，不擅自升级模式。

多候选起草的触发、隔离与综合由主 Agent 按 `competitive-drafting.md` 执行。候选起草仍是 `draft`：任务包中的强制先验只约束探索起点，不改变质量线、判断权和结果性质。

`quality_verifier` 的三类任务是触发条件，与本表是不同的轴：三类任务各自固定深度，不通过本表降档。

## 读取范围

只读取任务包列出的文件和自己的 `knowledge/roles/<role>.md`。共享 Knowledge 由主 Agent 在打包时按需附上；任务包未列出且结果确实依赖时，向主 Agent 索取路径，不自行整目录扫描。

## 结果性质

你的输出在主 Agent 签署前一律是 `agent_proposal`。逐项区分：用户原话、正式产物路径+条款/ID+revision、verified as-built、外部证据、推论、假设、建议、未知。不得把自己的判断标记为 `user_confirmed`、`accepted` 或“现有合同已足够”，也不得从“完成设计和开发”这类宽泛命令推断用户已选择你的方案。

任务包与用户最新约束、正式产物或当前 revision 冲突时停止并交回主 Agent，不自行选择一个版本继续。

## 写入边界

默认只返回结果。需要落盘时只写任务包明确授权的精确路径；目录名不产生长期所有权。不修改共享单点文件、正式产品状态或 `changes/`；`knowledge/` 各路径的 writer 以 [`.codex/rules/ownership.md`](../../.codex/rules/ownership.md) 的路径所有权表为准（`knowledge_curator` 在任务包授权下写入属正常职责，不构成放宽）。同一文件同一时间只有一个 writer。

writer 任务的失败、超时、越界、状态转换与重试按 [`.codex/rules/ownership.md`](../../.codex/rules/ownership.md)。

## 权限覆盖

任务包可以**收窄**角色 TOML 的搜索档位与写入范围，收窄立即生效。

**放宽**须由主 Agent 在任务包中显式声明并写明用户授权来源。没有来源的放宽按无效处理：按 TOML 档位执行，并把该冲突交回主 Agent。

## 外部操作

改变工作区之外状态的行为必须先由主 Agent 取得用户明确授权；需授权的操作清单以 `AGENTS.md`「写入、外部操作与汇报」为唯一定义。

公开 Web 搜索的权限按各角色 TOML 的档位执行；允许搜索时无需逐次询问，但必须引用来源与日期，并把事实与判断分开。

## 交付格式

使用中文自然语言。`draft` 模式按角色知识的交付物模板组织；其余模式按上方任务模式表。任何模式都包含：使用的合同来源与 revision、风险与未知项、需主 Agent 决定的问题、重要文件路径。

实现与验证类角色返回紧凑 envelope：`status`、`summary`、`findingIds`、`changedFiles`、`verificationIds`、`resultPath`/`resultHash`、`risks`。需要长报告时只写任务包唯一授权的 result path，不在最终消息重复全文。

局部自检不等于开发质量检查，也不等于正式验收。
