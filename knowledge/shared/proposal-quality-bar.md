# 设计/产品方案质量线

读取时机：主 Agent 为设计或产品类 `draft`/`revise`/`compare` 任务装配任务包时附上本文件路径；被派角色在任务包附有本文件时于起草前读取，返回前对照自查。

## 定位

本文件回答"动手之前，什么算一份好方案"，供生成端使用：角色在起草时对照，而不是交稿后由别人评。它只有定性判据，没有分数——计分、扣分、门禁与 Panel 机制的唯一定义在 `design-proposal-loop` 的 `references/evaluation-rubric.md`，那是本质量线在 98 分循环中的计分实例；两边不互相复制。

质量线不是合同：达不到某条不禁止交稿，但必须在"风险与未知项"里显式列出，不得沉默交付。

## 质量判据

起草时逐条对照；返回前答不出"是"的项写进风险与未知项：

1. **需求闭环**——每个 MUST 级目标或 Need 都能指出承接它的具体机制和用户可观察的成功信号，而不是"该页面支持此功能"式的宣称。
2. **旅程有效**——从真实入口到结果的路径完整，覆盖首次使用、高频使用和中断恢复中本轮适用的情境；相邻步骤之间没有"用户不知道下一步在哪"的信息断层。
3. **可理解与反馈**——用户在每个关键点能回答：我在哪、我能做什么、系统正处于什么状态、刚才的动作产生了什么结果、下一步是什么。
4. **控制与容错**——取消、撤销、重试、错误后输入保留、破坏性操作确认在适用处有设计；错误恢复写明用户下一步能做什么，不止"提示错误"。
5. **结构一致且可实施**——对象、命名、页面职责、业务规则之间无自相矛盾；方案能指导实现且能被验收，不存在"无法判断做没做到"的条款。
6. **取舍显式**——存在多个合理答案的结构决定摆成待确认差异（各自适合谁、各自代价、定下来需要哪个事实），不自选后掩盖；被否掉的备选和否掉理由保留。

各专业面的完整方法与交付骨架在 `knowledge/roles/<role>.md`；本清单不替代角色自检清单，两者都要过。

## 判例供给

角色强烈参照它见过的样本，判例是提高产出下限最直接的输入：

- **沉淀**：一份方案被用户确认并由主 Agent 签署后，若其结构取舍对同类问题有复用价值，主 Agent 交 `knowledge_curator` 蒸馏进对应角色的 `knowledge/roles/<role>.md` 判例节。蒸馏必须保留：当时的问题、最终结构、关键取舍理由、被否方案及否掉原因；剥离一次性的项目细节。
- **注入**：装配设计/产品类 `draft` 任务包时，若角色判例节存在与本轮问题同类的判例，把该判例章节列进"相关资料"。
- **边界**：判例是参照不是合同——与本轮已确认事实冲突时以事实为准；角色不得以"判例这么做"替代对当前问题的判断。

## 完成标准

- [ ] 设计/产品类 `draft`/`revise`/`compare` 任务包附有本文件路径和适用判例。
- [ ] 返回的方案对六条判据逐条可回答"是"，或该项已列入风险与未知项。
- [ ] 被签署的高价值方案有对应的判例蒸馏决定（做或明确不做）。
