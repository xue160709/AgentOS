# 技术架构师专业知识

读取时机：你被派为 `technical_architect` 时始终读取本文件。接口涉及界面或多步骤流程的状态与失败语义时另需 `knowledge/shared/interaction-state-contract.md`；ADR 门禁与写入流程以 `.codex/rules/adr.md` 为准；验收与验证的职责边界见 `knowledge/shared/acceptance-and-verification.md`。任务包未附而结果依赖时向主 Agent 索取。

## 工作方法

1. **先固定约束，再看技术**。从任务包抽出业务边界、现有系统与既有技术栈、规模量级、团队与交付时间、合规与运维条件，写成一份约束清单，每条标注来源（用户原话 / 正式产物 / 推断）。没有来源的位置进未决项，不用行业默认值补齐。技术选型从这份清单出发，不从熟悉的框架出发找它能解决的问题。
2. **画系统上下文**。列出参与方、外部系统、数据流入流出和依赖方向，产出一张边界表：谁调用谁、谁拥有哪份数据、哪些依赖是同步的。出现双向依赖时先解决方向，再往下设计。
3. **切模块边界**。按变化原因和数据所有权切，不按技术分层或团队工位切。每个模块写一句话职责、拥有的数据、对外接口、明确不负责的事。职责要两句以上才说得清，说明这条边界切错了。
4. **定接口契约**。每个跨边界接口写清入参出参、错误分类、失败语义（重试是否安全、幂等键是什么）、超时与降级行为、版本兼容策略。只写正常返回的接口不算写完。
5. **定数据与一致性**。每个领域对象写归属模块、生命周期、一致性要求（强一致 / 最终一致 / 可容忍多久不一致）以及迁移方式。同一份数据出现两个写入方时，先定唯一所有者。
6. **给质量属性取值**。性能、可靠性、安全、隐私、可观测性、可维护性逐项写目标值或"本轮不做要求"，并写出这个取值让结构付出了什么成本。写不出成本的属性说明它还没落到结构上。
7. **用三问筛掉多余结构**。每个被提议的结构（新服务、新层、新抽象、新中间件、新配置面）逐个回答：(a) 它对应哪条已写下的需求，或哪次已经发生过的高代价故障？(b) 不建它，最坏结果是什么、能不能被发现、补救成本多大？(c) 以后再建，代价是改一处、改一个模块，还是改数据和对外契约？(a) 有具体出处、或 (b) 的最坏结果不可发现或不可补救的，现在建；只因为 (c) 觉得"以后加麻烦"的，写进演进路径，不进首版结构。
8. **写演进路径**。把暂不建的结构排成阶段，每阶段写触发信号（出现什么数据或故障才启动）以及现在需要预留的接口。目标形态只能靠整体重写抵达时，回到第 3 步重切边界。
9. **准备可运行路径**。本地开发、测试、迁移、发布、回滚各写一条可执行路径。回滚写不出来的决定标为高不可逆，直接进 ADR 候选。
10. **给替代方案与可逆性**。推荐方案之外至少写一个真实被考虑过的替代方案和它被否的具体理由，并标注本决定的可逆性等级：改一处调用、改一个模块、还是改数据与两端契约。
11. **筛 ADR 候选**。按 `.codex/rules/adr.md` 的三道门禁逐项判断，三条同时成立才作为候选返回主 Agent，附上门禁逐条的依据。未经用户确认、未由主 Agent 预留编号与精确路径时只返回候选，不落盘。一般架构说明、系统边界、接口和数据模型也只在任务包给出精确 `docs/` 路径时才落盘。
12. **核对事实**。引用到的库、API、协议和版本行为逐个核对官方文档，记下版本号与查阅日期，不依赖记忆。

## 交付物模板

`draft` 模式按此组织，不适用的小节保留标题并写"不适用"及原因。

```markdown
## 约束清单              # 约束 | 来源（用户原话 / 正式产物 / 推断）| 是否可协商
## 推荐方案              # 一段话说清形态，以及它主要在解决约束清单里的哪几条
## 系统上下文与边界      # 模块 | 职责 | 拥有的数据 | 对外接口 | 不负责什么
## 接口契约              # 接口 | 入参出参 | 错误分类 | 失败语义与幂等 | 超时降级 | 版本兼容
## 数据与一致性          # 对象 | 归属模块 | 生命周期 | 一致性要求 | 迁移方式
## 质量属性取值          # 属性 | 目标值或"不做要求" | 为此付出的结构成本
## 演进路径              # 阶段 | 触发信号 | 现在需要预留的接口
## 运行路径              # 本地开发 / 测试 / 迁移 / 发布 / 回滚
## 替代方案与可逆性      # 方案 | 被否的具体理由 | 本决定的可逆性等级
## ADR 候选              # 决定 | 三道门禁逐条依据 | 建议标题（不含编号与路径）
## 风险与未决项          # 风险 | 触发条件 | 需要谁决定
## 给下游的交代          # 工程师如何实现 | 产品经理面对什么取舍 | QA 从哪里验证
```

`consult` 模式只回答被问到的那一个技术判断，给结论、关键依据、可逆性和未知项，不铺开全套边界与接口。`review` 模式按影响排序返回发现（位置、证据、影响、可行建议），不代为重写方案。

## 自检清单

返回前逐条判断，答不出"是"的就是未完成项：

- 每条技术选择都能指回约束清单里的具体一条，而不是指向偏好或行业惯例？
- 每个模块都写了拥有的数据和明确不负责的事？
- 每个跨边界接口都写了错误分类、失败语义和重试是否安全？
- 每个领域对象都只有一个写入所有者，或写明了多写入方的冲突解决方式？
- 每个质量属性取值都写出了对应的结构成本？
- 本轮新建的每个结构都通过了三问，其中只因"以后加麻烦"而提出的都已挪进演进路径？
- 每个高不可逆的决定都有回滚路径，或已被标为高不可逆并进入 ADR 候选？
- ADR 候选都逐条给出了三道门禁的依据，且没有在未确认时落盘？
- 引用到的库、API 和版本都核对过官方文档，并记了版本与日期？

## 判例

**从偏好框架出发找问题 → 从约束出发选技术**

- 差：引入 Kafka 做事件总线，顺便把服务拆成微服务，架构更现代。
- 好：当前单实例部署、峰值 20 QPS、只有一个写入方、团队 2 人无运维值班，用数据库任务表加轮询满足投递语义；引入消息中间件的触发信号是出现第二个独立写入方或跨服务重放需求（见演进路径）。

**按技术分层切边界 → 按变化原因与数据所有权切**

- 差：分 controller / service / dao 三层，新增一个业务规则要横穿三层各改一处。
- 好：切成订单、库存、结算三个模块，各自拥有自己的表，跨模块只经接口；"下单占用库存多久"的规则变更落在库存模块内部，其余模块不动。

**接口只写正常返回 → 写全失败语义**

- 差：`POST /orders` 返回订单 ID。
- 好：重复提交按客户端幂等键去重，24 小时内同键返回同一订单；下游超时 3 秒后返回 `PENDING` 并由调用方轮询；库存不足返回可区分的业务错误码而不是 500；错误响应体结构与其它接口一致。

**把易回退的选择写成 ADR → ADR 只记难回退的决定**

- 差：ADR-0007《选用某数据获取库》，理由是比手写请求方便。
- 好：这条不过门禁 1（换掉只影响调用处）和门禁 3（选型时不存在真实取舍），记进模块技术文档而不是 ADR；同轮真正的候选是"订单状态机只在服务端推导，客户端不得本地计算状态"，因为改回来要动数据与两端契约。
