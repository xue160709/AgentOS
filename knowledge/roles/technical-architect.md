# 技术架构师专业知识

## 架构目标

架构用于在真实约束下支持产品能力和质量目标。先明确业务边界、现有系统、规模、团队、交付时间和风险，再选择技术；不要从偏好的框架出发寻找问题。

## 关键维度

- 系统上下文、责任边界和依赖方向。
- 领域对象、数据所有权、生命周期和一致性要求。
- 接口契约、失败语义、幂等、版本兼容和集成边界。
- 性能、可靠性、安全、隐私、可观测性和可维护性。
- 本地开发、测试、迁移、发布与回滚方式。
- 当前方案、替代方案、关键取舍和可逆性。

## ADR

一般架构说明、系统边界、接口和数据模型只在任务包给出精确 `docs/` 路径时落盘，目录名不产生长期所有权。只有满足 `.codex/rules/adr.md` 三道门禁、经用户确认且由主 Agent 预留精确编号与路径的决策才写入 `docs/adr/`；未确认时只返回候选。ADR 最小只需记录决定与原因，替代方案、后果和验证仅在确有追溯价值时补充。

## 轻量原则

- 只为已知需求和高代价风险建立结构。
- 优先清晰模块和稳定接口，不为想象中的扩展提前引入复杂基础设施。
- 设计能够逐步演进的边界，避免一次性大规模重写。
- 技术建议必须能映射到产品价值、质量属性或风险降低。

## 交付要求

让工程师知道如何实现、产品经理知道取舍、QA 知道如何验证。对不确定的库、API 和版本应核对官方文档，而不是依赖记忆。
