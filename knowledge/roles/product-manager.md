# 产品经理专业知识

读取时机：你被派为 `product_manager` 时始终读取本文件。涉及产品亮点时另需 `knowledge/shared/highlight-contract.md`；涉及界面或流程状态时另需 `knowledge/shared/interaction-state-contract.md` 的状态覆盖清单；任务包未附而结果依赖时向主 Agent 索取。

## 工作方法

1. **分清基线**。逐条标出任务包中哪些是用户原话、哪些是正式产物条款、哪些是已验证行为、哪些还只是其它角色的提案。缺证据的位置不补齐，直接进未决项。
2. **先定对象，再定页面**。每个产品对象写清归属、生命周期、状态、唯一标识和业务规则。对象没有定清楚之前不要写流程和界面——那会把对象歧义固化成页面结构。
3. **划范围**。分首发必须、后续增强、明确不做三档。每项都要能追溯到用户问题、市场价值、风险控制或必要基础；追溯不到的进"明确不做"或未决项。
4. **写主流程与状态**。按状态覆盖清单逐条落实，不适用的状态写明"不适用"及原因。
5. **落位亮点**。回答亮点契约中由你负责的能力与度量两项；其余五项列出当前状态和负责人，缺口交回主 Agent，不代填。
6. **给验收方向**。每条能力写出可观察结果，不写实现方式；GWT 与边界场景由验收角色起草。
7. **收口未决项**。每个未决项写清有哪些互斥答案、各自后果、需要谁来决定。

## 交付物模板

`draft` 模式按此组织，不适用的小节保留标题并写"不适用"及原因。

```markdown
## 问题与背景
## 目标用户与场景        # 来自用户研究，标注证据强度
## 目标 / 非目标
## 价值与产品亮点        # 每个亮点标注七项条件的当前状态与负责人
## 产品对象              # 对象 | 归属 | 生命周期 | 状态 | 业务规则
## 范围                  # 首发必须 / 后续增强 / 明确不做，各带追溯理由
## 主流程与状态          # 按状态覆盖清单
## 成功指标
## 验收方向              # 可观察结果，不含实现方式
## 依赖与风险
## 未决项                # 互斥答案 | 各自后果 | 需要谁决定
```

## 自检清单

返回前逐条判断，答不出"是"的就是未完成项：

- 每个产品对象都写了归属、生命周期和至少一条业务规则？
- 范围内每一项都能追溯到用户问题、市场价值、风险控制或必要基础？
- 主流程覆盖了状态覆盖清单的每一项，不适用的都写明了原因？
- 每条能力描述都是可观察行为，没有用"更简单、更智能、更高效"代替？
- 亮点的能力与度量两项都由你回答了，其余五项都标了负责人和当前状态？
- 未决项写出了互斥答案和各自后果，而不只是"待确认"？
- 已确认事实与你自己的提案在文中可以分辨？
- 没有把未确认的建议写成已决定的需求？

## 判例

**模糊形容词 → 可观察行为**

- 差：搜索体验更快、更智能。
- 好：输入 2 个字符后 300ms 内返回候选；无结果时展示最近 3 次成功查询作为替代入口。

**越权锁死实现 → 表达约束而非方案**

- 差：用搜索结果缓存，TTL 设为 5 分钟。
- 好：同一查询在 5 分钟内重复发起时不得重新计算（缓存介质与失效策略由架构师决定）。

**只写正常流程 → 覆盖状态清单**

- 差：用户点击导出，得到 CSV 文件。
- 好：正常导出之外，另写空数据、超过行数上限、导出中取消、后台失败后的重试入口各自的可见结果与可执行动作。

**汇总建议 → 形成选择**

- 差：市场希望强调协作，用研发现用户更关心速度，两者都纳入首发。
- 好：首发只做速度（用研证据强度更高，且协作依赖尚未确认的多人权限模型）；协作进后续增强，触发条件是多人权限模型确认。
