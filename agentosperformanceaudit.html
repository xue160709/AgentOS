AgentOS 性能体检

对 homepage-test 分支做的一次静态代码审查加真实数据测量。结论先行：应用最重的成本不在渲染，而在“每收到一批流式 token 就把整个工作区读一遍、存三遍、再广播一遍”。其它问题（首屏包体、AppShell 巨型组件、CSS 体积）都是第二梯队。

仓库 CodeX-UI-Template (AgentOS 0.1.17) 日期 2026-09-02 测量数据源 ~/Library/Application Support/AgentOS 方法 代码追踪 + Node 计时 + sqlite3 计时 + 产物体积

总体判断：一条主进程热路径决定了整体手感

Agent 回复流式输出时，主进程 broker 对每一个合并后的 delta 事件（50ms 窗口，最高约 20 次/秒）都会同步读取 5MB 的工作区 JSON 两次、重写全部 63 个会话 rollout 文件、同步 spawn 三次 sqlite3 CLI 并全量重建搜索索引，再把包含 base64 附件的完整项目快照通过 IPC 广播给渲染进程。渲染进程这边同一事件又会把整个工作区 JSON.stringify 两次并同步写入 localStorage。这条链路是 CPU、磁盘和 IPC 的共同瓶颈，也是所有窗口在 Agent 运行期间“发黏”的根因。

问题清单按影响排序，每条附证据与修复方案

P0-1

主进程对每个流式事件做全量工作区读、写、索引重建

Critical

这是整体性能的第一瓶颈。成本随工作区总大小线性增长，与当前对话无关：用户历史越多，每个 token 越慢。同步 spawn 会冻结主进程，影响所有窗口。

证据

  • electron/chat-broker-core.ts:373-394：每个事件依次调用 saveThreadChatState 和 broadcast。
  • electron/project-chat-broker.ts:111-117：saveThreadChatState 先 store.read()，再 saveMutation 调 store.save() 保存整个工作区。
  • electron/chat-workspace-store.ts:197-222：save() 顺序执行 saveRolloutFiles（重写所有线程）、saveDatabaseIndex（全量 upsert + 搜索索引 DELETE/重建）、saveJsonSnapshot（5MB 缩进 JSON）。
  • electron/chat-workspace-store.ts:654-665：runSql / selectJson 都是 execFileSync('sqlite3', …)。
  • electron/chat-workspace-store.ts:329-333：read() 每次都从磁盘 readFileSync + JSON.parse，不用内存中的 currentState；全仓 48 处调用。
  • 实测：5MB 文件 parse 6.5ms，stringify 2.6-7.7ms，sqlite3 单次 spawn 约 3ms，索引重建约 25ms。加上 65 次文件写与两次 5MB 读，单事件主线程占用估计 50-100ms，20 次/秒即饱和。

修复

  1. 流式期间不落盘。delta 只更新内存中的线程状态并广播增量事件；只在 result / error / cancelled 或 5-10 秒节流时持久化。
  2. 按线程增量保存。只重写发生变化的那一个 rollout 文件；sqlite 只 upsert 变化的线程行；搜索索引改为按 thread_id 删除后重插，而不是全表 DELETE。
  3. 用 current() 替换热路径上的 read()，read() 只在启动和外部修改时调用。
  4. 把 sqlite3 CLI 换成进程内驱动（node:sqlite、better-sqlite3 或 sql.js），或至少改为异步 execFile 并串行排队，避免阻塞事件循环。
P0-2

渲染进程每次状态更新同步序列化并写入 localStorage 整个工作区

Critical

UI 线程上每个 delta 做两次 5MB 的 JSON.stringify 和一次 5MB 的 localStorage 同步写，直接吃掉帧预算，流式输出时的卡顿主要来自这里。localStorage 目录已膨胀到 37MB。

证据

  • src/components/workspace-session.ts:290-305：stage() 对每次更新都调用 prepareDurableSave（指纹）和 saveImmediateState（localStorage）。
  • src/workspace-snapshot-resolution.ts:87-90：指纹就是整个工作区的 JSON.stringify。
  • src/chat-workspace-persistence.ts:181-191：localStorage.setItem 写整个工作区，异常被 catch {} 吞掉。
  • 实测：当前载荷 4,971,857 字符。Chromium 每源 localStorage 配额约 10MB（按 UTF-16 计约 5M 字符），已贴近上限；一旦超限写入会静默失败，回退快照将过期而无人知晓。此条为推断，建议在 DevTools 中验证 setItem 是否已抛 QuotaExceededError。

修复

  1. localStorage 只保留轻量元数据（活动线程、侧栏偏好、tab），线程正文由主进程负责持久化。
  2. 指纹换成廉价方案：比较 workspaceRevision 或对象引用，不再序列化整树。
  3. 把 stage() 的即时写改为 idle 回调或 250-500ms 节流，并把流式 delta 排除在“需要落盘”的变更之外。
P0-3

图片附件以 base64 内联在对话记录里，被复制到每一层

Critical

两张图片（1.59MB + 0.66MB）占整个工作区的 45%，随每次保存、每次 IPC 快照、localStorage 镜像和 React 状态一起被复制。这是 P0-1 和 P0-2 数量级的放大器。

证据

  • 实测：线程 thread-mpnavr43-85yzpz 38 条记录 2.27MB，其中 message.attachments 字段 2,255,776 字节。
  • src/claude-chat-types.ts:59：附件类型带 dataUrl；electron/project-chat-broker.ts:530 的 projectChatTranscriptItem 把 dataUrl 原样放进广播快照。
  • electron/main.ts:312：单张图片上限 5MB，8 个文件总量上限 24MB，意味着单个线程理论上可膨胀到 30MB 以上。

修复

  1. 附件落成文件：保存到 userData/attachments/<hash>，记录里只留 id、mime、size 和一张小缩略图。
  2. 渲染时通过自定义 protocol 或 file URL 引用，不进入 JSON、IPC 与 localStorage。
  3. 做一次迁移把现有内联附件外置，立刻把工作区文件缩小一半。
P1-4

对话状态挂在 AppShell，每个 delta 让整个壳层重新 render

High

AppShell 是 3,314 行的单体组件。setChatWorkspace 在它内部，因此每个 delta 都触发 AppShell、ChatPage、AppShellSidebar、AppShellWorkspace、Composer 的完整 render。Transcript 做了 memo，但正在增长的那条消息每次都从头做 Markdown 解析。

证据

  • src/components/AppShell.tsx:1365-1370：updateThreadChatState → updateChatWorkspace → setChatWorkspace。
  • src/components/chat/ChatPage.tsx:343 是 forwardRef 而非 memo；AppShellSidebar / AppShellWorkspace / Composer / ProjectHomeSurface 均未 memo。
  • src/components/chat/Transcript.tsx:571：useMemo(() => renderMarkdownSegments(content), [content])，流式中 content 每次都变，marked + KaTeX + DOMPurify 全量重跑。
  • src/components/chat/RichCodeBlock.tsx:120-160：MermaidDiagram 的 effect 依赖 code，流式中未闭合的 mermaid 块每个 delta 都触发 render 与修复候选重试。
  • src/components/chat/Transcript.tsx:152-162：运行期间 1 秒定时器在 Transcript 根节点 setState。
  • 没有列表虚拟化；最长线程 147 条记录全部挂在 DOM 上。

修复

  1. 把线程 chatState 从 AppShell 拆出，放到独立 store（useSyncExternalStore / zustand 风格）并按 threadId 订阅，壳层只订阅元数据。
  2. 流式消息用增量渲染：只解析最后一个未完成 block，之前已完成的段落缓存 HTML；mermaid 只在代码块闭合或流式结束后渲染。
  3. 给 ChatPage、Sidebar、Workspace、Composer 加 memo，并把 useLiveNow 下沉到只显示时长的那个小组件。
  4. 超过约 100 条记录时启用虚拟列表。
P1-5

首屏加载把设置页、A2UI、KaTeX 样式和 59 个字体文件一起带上

High

冷启动要解析 1.37MB JS 与 297KB CSS，没有任何路由级代码分割。主进程 main.js 也有 1.4MB，zod 被完整打进去。窗口未使用 ready-to-show，首帧可能白屏。

证据

  • dist/assets/index-JZi1oWqr.js 1,369,951 字节（gzip 388,646），其中 a2ui 标识 200 处、lit 135 处、mermaid 胶水 40 处。
  • 全仓没有 React.lazy / Suspense；ClaudeAgentSettingsPage（2,286 行）和 ProjectHomeSurface（3,845 行，A2UI）随首屏加载。
  • src/main.tsx:6 静态引入 katex/dist/katex.min.css，把 59 个字体文件（1.1MB）带进产物。
  • dist-electron/main.js 1,398,457 字节，zod 引用 269 处。
  • electron/main.ts:376-398：主窗口未设 show: false + ready-to-show。
  • 做得对的地方：mermaid 已按需加载（cytoscape、wardley 等 600KB 级块不影响首屏）。

修复

  1. 路由级 lazy：设置页、ProjectHomeSurface、RuntimeDevelopmentWindowPage、AppSearchModal 用 React.lazy。
  2. KaTeX CSS 改为在首次遇到公式时动态注入，并只保留 woff2 字体。
  3. vite 配置 manualChunks 把 react、a2ui、marked 分开，便于缓存与分析；加 rollup-plugin-visualizer 做一次可视化。
  4. 主窗口 show:false + ready-to-show，避免白屏。
P2-6

CSS 是一个 10,881 行的单文件，且透明窗口叠加大量模糊滤镜

Medium

首屏 CSS 297KB；858 个类里有 126 个在源码中找不到引用。macOS 下窗口是 transparent + vibrancy，再叠 28 处 backdrop-filter 与 26 处 blur，滚动和流式重绘时 GPU 合成成本明显。

证据

  • src/style.css 281,392 字节、1,569 条规则、19 处通配选择器、76 处 box-shadow。
  • electron/main.ts:389-396：transparent: true, vibrancy: 'under-window'。

修复

  1. 按组件拆分 CSS 并用 vite 的 CSS code-splitting 随 lazy 路由加载。
  2. 清理未引用的 126 个类（先用 PurgeCSS 报告确认再删）。
  3. 把 backdrop-filter 限制在侧栏和弹层，滚动区域内的元素不使用模糊。

已经做对的地方修改时不要顺手退化

主进程 delta 合并器50ms 窗口把 token 级事件压到最多 20 次/秒，是正确的第一道闸。
mermaid 按需加载1.6MB 的图表家族完全不进首屏。
Transcript 行级 memoChatMessage、ToolRow、ThinkingRow 等都用了 memo，只是上游状态设计让它们收益有限。
